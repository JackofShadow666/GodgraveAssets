# Правила проекта

## 🛑 Ограничения контекста
- Для интернета используй минимум поиска (только при крайней необходимости).

## 💬 Правила коммуникации
- Сухой ответ: Пиши только техническую суть (код, файлы, ошибки). Полностью исключи вежливость, приветствия, вводные слова и повторение моих фраз.
- Поэтапный опрос: Если не хватает вводных, не гадай. Задай ровно 1 короткий вопрос за раз.
- Готовые опции: К каждому вопросу обязательно предлагай 2-3 варианта ответа (например: "1) Да, 2) Нет, 3) Свой вариант"), чтобы я мог ответить одной цифрой.
- Активация Grill Me: При явном вызове команд `/grill-me`, `/grilling` или `$grill-me` строго переключайся в глубокое интервью по Режиму 3.

---

## Режимы задач
Сам определяй режим задачи перед работой и выбирай самый дешевый достаточный путь.

### 1. Мелкая правка
Признаки: точечный UI/баланс/текст/цвет/число, понятный модуль, низкий риск.
- Сначала используй src/MAP.md, если файл не указан.
- Не делай широкий поиск по проекту, если карта дает очевидный файл.
- Читай только целевой файл и ближайший AGENTS.md (при наличии).
- Не запускай тесты, сборку и git без явной пользы или просьбы.
- Если за 1-2 чтения файлов место правки не найдено, задай вопрос или перейди в режим 3.

### 2. Пак правок
Признаки: несколько мелких связанных изменений в одной зоне.
- Сначала составь короткий список затрагиваемых зон по MAP.md.
- Читай только файлы из этих зон.
- Делай правки пачкой, без лишнего рефакторинга.
- Проверяй только затронутый сценарий.

### 3. Неопределенная или сложная задача (Режим Grill Me)
Признаки: баг без понятной причины, новая механика, конфликт подсистем, онлайн/локальный режимы, высокий риск, либо прямой вызов команды `/grill-me`.
- **Инструкция Grill Me:** Категорически запрещено писать или изменять код, пока финальный технический план не утвержден пользователем.
- Проводи жесткое, последовательное интервью: задавай строго по 1 глубокому техническому вопросу за ход.
- Копай в крайние случаи (edge cases), обработку ошибок, производительность и совместимость с build.py.
- Соблюдай правила коммуникации: пиши сухо, без вежливости, предлагай 2-3 варианта ответа для выбора цифрой.
- Перед правкой назови релевантные файлы и выведи финальный короткий план. Напиши «План утвержден!» и только после согласия переходи к коду.

### 4. Рефакторинг
Признаки: перенос ответственности, переименование, удаление дублей, изменение API между модулями.
- Сначала определи границы рефакторинга и риск.
- Используй поиск по проекту для всех вызовов и зависимостей.
- Не смешивай рефакторинг с несвязанными gameplay/UI правками.
- После рефакторинга обязательно обнови MAP.md.
- По возможности проверь затронутые сценарии или явно напиши, что не проверялось.

---

## Карта проекта
- MAP.md является первым маршрутизатором для задач по src.
- Если карты нет, создай ее перед работой по src.
- Обновляй карту, когда добавлен/удален/переименован файл, изменилась зона ответственности модуля, появился новый быстрый маршрут или старая запись стала вводить в заблуждение.
