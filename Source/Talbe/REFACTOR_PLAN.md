# Карта модулей и план разбивки на файлы

Файл: `Combo_77_3__10_multibots_2_fixed_6_3__4__1__2__3.html`

## ✅ Сделано: виртуальное разбиение на слои внутри файла

Первый `<script>` (игровая логика) физически переупорядочен внутри одного файла
по принципу **CORE → системы → геймплей → bootstrap** (аналог `Blizzard.j`   — общий "движок" снизу, конкретная карта/логика сверху). Файл
всё ещё один `<script>`, но порядок кода внутри него теперь соответствует
тому, как модули будут вынесены в отдельные файлы в будущем.

Слои в порядке подключения (каждый использует только то, что объявлено в нём
самом или в слоях выше):

искать по `grep -n "^// LAYER:" game.html`.

### Как это проверено

Разбивка построена не вручную построчно, а через настоящий JS-парсер (AST),
чтобы не задеть код внутри тела функций и гарантированно не потерять и не
задвоить ни одной строки:

1. Каждое top-level объявление (переменная/функция) и его код классифицированы по слою.
2. Проверено, что ни один слой не использует на верхнем уровне (вне функций) переменную,
   объявленную в слое, идущем позже него — иначе в реальном порядке файлов это привело бы
   к `ReferenceError: Cannot access '...' before initialization`.
3. Итоговый файл выполнен целиком в эмуляции браузерного окружения (мок `canvas`/`document`/
   `window`) — весь top-level код действительно проходит инициализацию без ошибок, а не
   только проходит проверку синтаксиса.
4. Сверено, что каждое имя функции/переменной верхнего уровня объявлено ровно один раз
   (без потерь и дублей) до и после реорганизации.

### Важный нюанс про function hoisting

`function`-объявления в JS видны в любом порядке файлов (hoisting работает
между `<script>`-тегами тоже) — поэтому реальный риск был только у `const`/`let`,
используемых в *исполняемом* коде верхнего уровня (не внутри функций). Единственная
найденная и исправленная опасность такого рода — вызов `initBoxes()` (использует
`const BOXES`), который должен идти строго после объявления `BOXES` в слое COMBAT;
теперь он вынесен в отдельный слой BOOTSTRAP в самом конце, вместе с `loadAudioDB()`
и `requestAnimationFrame(loop)`.

## Следующий шаг (когда будет готовность): физический вынос в файлы

Поскольку слои уже выстроены в правильном порядке зависимостей внутри одного файла,
следующий шаг — механический: взять текст между `// LAYER: X` и `// END LAYER: X`,
сохранить в `X.js`, и в HTML заменить это место на `<script src="X.js"></script>`
в том же порядке. Рекомендуется делать по одному слою за раз, начиная с `core.js`
(наиболее независимый), и проверять игру в браузере после каждого выноса — риск
уже сильно ниже благодаря тому, что порядок зависимостей проверен, но браузер —
не Node.js, и стоит убедиться визуально, что ничего не сломалось на каждом шаге.
